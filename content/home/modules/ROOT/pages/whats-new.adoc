= What's new across the Vidocq ecosystem
:description: Which components have something new on the development line, and where each one lists it.

[.lead]
A component with something to announce keeps its own What's new page on its `dev` documentation line: it lists what landed after that component's last release, and each entry links to the section that documents it — the section carrying the [.tag-new]#NEW# badge. This page is the entry point to those lists. It names the components that have something today, and says what it is, so you can go straight to the one you work with.

== Components with something new

=== Vidocq Runtime — startup identity, console logs, Maven goals

* **Booting says what it is.** Every start prints the exact Vidocq version, with the commit for a snapshot or a build from a modified tree, then the launch mode — `dev`, `test` or `prod` — together with the signal it was read from, and the address a debugger has to attach to when the JVM was started with a JDWP agent.
* **Every jar carries its build identity** under `META-INF/vidocq/build-info/`, so two snapshots of the same version are told apart.
* **Readable console logs by default.** An application that has not configured logging gets one aligned line per record on standard output, instead of the JDK's two-line records on standard error.
* **Running from Maven.** `vidocq:run` compiles, indexes and runs the application in a forked JVM the way the production launcher does, and the experimental `vidocq:idea` goal writes the matching IntelliJ run configurations into `.run/`.

Full list: xref:dev@vidocq::whats-new.adoc[What's new in Vidocq Runtime].

=== Vauban — client proxies without `opens`, Java SE launcher

* **A client proxy for a third-party produced type, without opening its package.** The Java SE launcher `io.vidocq.vauban.classloader.Launch` runs the application inside a Vauban layer, where the proxy is placed into the type's own package by the loader that owns it — no `opens`, no agent, no rewritten jar — and `Vidocq.run` re-layers with the same policy.
* **Boot-time opening is opt-in**, `-Dvauban.opens.auto=true`, and off by default; left off, the container refuses and names every remedy.
* **Two opt-in Maven goals.** `vauban:modularize` synthesizes a `module-info` for the non-modular dependency jars; `vauban:enhance-dependencies` is the last-resort copy of a dependency jar with the proxy co-located in it.

Full list: xref:dev@vauban::whats-new.adoc[What's new in Vauban].

=== Cassini — unreadable request entities answer 400

* **A client's malformed request entity is the client's fault.** Malformed JSON, an empty body or a value of the wrong type now answers `400 Bad Request` instead of `500`, after the application's own exception mappers, and no longer writes a stack trace at ERROR for every such request — one DEBUG line instead.
* **`NoContentException` becomes a `BadRequestException`**, whatever reader throws it, as Jakarta REST §4.2.4 requires.

Full list: xref:dev@cassini::whats-new.adoc[What's new in Cassini].

== How these lists are maintained

This page is versionless, so a link from here to a component resolves against that component's latest **released** documentation unless it says otherwise. The links above are therefore pinned with `dev@`. Today that pin is what makes them resolve at all — no released line carries a What's new page, the practice being younger than the 0.3.0 cut. From the next release train on, each released line will carry the page frozen with it, and an unpinned link would quietly land on that frozen list instead of the one this index is about.

When the next release train ships, each component's page is frozen with its released documentation and restarts empty on `dev`, and the [.tag-new]#NEW# badges are stripped from the pages they were flagging. The release cut does not touch this page: it has to be updated by hand when a component starts or stops having something to announce.
