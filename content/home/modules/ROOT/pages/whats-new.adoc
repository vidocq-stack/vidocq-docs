= What's new across the Vidocq ecosystem
:description: Which components have something new since the 0.4.0-RC1 release, and where each one lists it.

[.lead]
Each component keeps its own What's new page on its `dev` documentation line: it lists what landed after that component's last release (0.4.0-RC1, cut on 2026-10-26), and each entry links to the section that documents it — the section carrying the [.tag-new]#NEW# badge. This page is the entry point to those lists. It says what is new across the components, then where each one lists it.

== The big changes since 0.4.0-RC1

Most of the work since RC1 follows one rule: Vidocq generates at build time what other runtimes do by reflection at start-up, and *the CLI and the Maven plugin carry the build-time constraints, not you*. A tutorial written and replayed from `vidocq create` to a Docker image found every place where that was not yet true; the list below is what changed.

=== Java modules: the tooling writes the directives

* **One check, written for you** — `vidocq doctor` and the build check the same module directives, the `opens` of the application's own packages included: the JPA entities, the types a REST resource takes or returns (through fields, getters, superclasses and implementations), the interceptors with a private method. `vidocq dev` writes a missing `opens` itself, `vidocq doctor --fix` and `vidocq:complete-module-info` write them on demand, and all of them keep one block marked `// vidocq:reflection`.
* **A clear message at run time** — a package the runtime cannot reach, and the build could not see, fails with the package and the `opens` line to add; under `vidocq dev` the line is written and the application reloads.
* **Or no directive at all** — `vidocq create --open-module` creates an `open module`.

Read: xref:dev@vidocq::java-modules.adoc[Java modules in a Vidocq application].

=== Less reflection in an application

* **JSON-B bindings generated at build time** — Champollion generates the binding of the records and final classes a REST resource exchanges, with no annotation, so JSON-B maps them without reflection. xref:dev@champollion::reference.adoc#rest-bindings[Champollion].
* **Interceptor methods called by generated code** — Vauban calls `@AroundInvoke`, `@AroundConstruct` and lifecycle interceptor methods through the provider generated in their package: a package-private interceptor needs no `opens`. xref:dev@vauban::internals.adoc#components-provider[Vauban].
* **Repositories from a dependency jar** — a library's `@Repository` interfaces are implemented at build time, like the application's, by `vidocq:generate`. xref:dev@mansart::usage.adoc#dependency-repositories[Mansart], xref:dev@vidocq::whats-new.adoc[Vidocq].
* **Run-time generation is announced** — when Vauban, Cassini, Cyrano or Mansart must generate a class or serve a repository at run time instead of at build time, they say so in a framed warning at start-up.

=== The CLI does the setup

* **Dev services wired by `extension add`** — the dev-service provider, the JDBC driver and the test-scope pair are written into the `pom.xml`, the settings each extension needs into `vidocq.properties` (commented when only you can know the value), and `vidocq config set` uncomments a line in place. `vidocq doctor` and `vidocq:checkpom` warn about anything missing.
* **Docker from macOS and Windows** — `vidocq build docker` links the runtime image inside a Linux JDK stage of the Dockerfile and builds the image when Docker answers.
* **Quieter builds** — the "created in the last round" warnings are gone, Mansart's generated sources included.

Full list: xref:dev@vidocq::whats-new.adoc[What's new in Vidocq Runtime].

=== SNAPSHOTs on our own repositories

`main` of every component publishes its SNAPSHOTs to `https://maven.vidocq.dev/snapshots/`, copied every 10 minutes to `https://maven.bak.vidocq.dev/snapshots/`, then to Central's snapshot repository. `vidocq create` declares the first two. Releases stay on Maven Central.

== Component by component

* xref:dev@vidocq::whats-new.adoc[Vidocq Runtime] — the items above, plus JDBC spans with Telemetry, `--help` on every command, `vidocq test` reading the application's configuration, and the dev-service fixes.
* xref:dev@vauban::whats-new.adoc[Vauban] — dependency beans validated at build time, generation before javac's last round, generated interceptor invokers, overloaded `@Inject` constructors, run-time generation announced, dependency classes read without being initialised.
* xref:dev@champollion::whats-new.adoc[Champollion] — JSON-B bindings for REST types, an access error that names the `opens` to add, JSON-B and Protobuf conformance fixes, a cheaper JSON-P pipeline.
* xref:dev@mansart::whats-new.adoc[Mansart] — repositories from a library, Weld and Open Liberty, Jakarta Data conformance fixes (MANSART-010 to -023), a build error for a method no query derives from.
* xref:dev@cassini::whats-new.adoc[Cassini] — a lighter request path, `@PreMatching` filters run once, run-time adapters announced, Jakarta REST conformance and client fixes.
* xref:dev@cyrano::whats-new.adoc[Cyrano] — run-time clients announced, more interfaces served at build time, exceptions unchanged through interceptors.
* xref:dev@grimm::whats-new.adoc[Grimm] — the processor works under Maven, `@OpenAPIDefinition` read on Vidocq, the runtime's own endpoints left out, static-file fixes.
* xref:dev@humboldt::whats-new.adoc[Humboldt] — OpenTelemetry 1.67.0 (GHSA-ccrj-gw8r-854m), exporters default to OTLP, `http.route` is the template, no SDK test library in an application.
* xref:dev@heisenberg::whats-new.adoc[Heisenberg] — annotations read at compile time, `@Timeout` keeps the caller's context, policies resolved once.
* xref:dev@cervantes::whats-new.adoc[Cervantes] — the token stays out of `toString`.
* xref:dev@chappe::whats-new.adoc[Chappe] and xref:dev@dirac::whats-new.adoc[Dirac] — performance and build-time extension fixes.
* xref:dev@peano::whats-new.adoc[Peano] and xref:dev@ibarra::whats-new.adoc[Ibarra] — released in 0.4.0-RC1; small fixes since.

== How these lists are maintained

This page is versionless, so a link from here to a component resolves against that component's latest **released** documentation unless it says otherwise. The links to What's new pages are therefore pinned with `dev@`: the 0.4.0-RC1 line carries the page frozen at the release, and an unpinned link would land on that frozen list instead of the one this index is about.

When the next release train ships, each component's page is frozen with its released documentation and restarts empty on `dev`, and the [.tag-new]#NEW# badges are stripped from the pages they were flagging. The release cut does not touch this page: it is updated by hand when a component starts or stops having something to announce.
