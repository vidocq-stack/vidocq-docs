= What's new across the Vidocq ecosystem
:description: What changed across the Vidocq components from the 0.3.0 release to 0.4.0, release by release, and where each component lists it.

[.lead]
Each component keeps its own What's new page. After the 0.3.0 release the ecosystem shipped two release candidates, 0.4.0-RC1 (2026-10-26) and 0.4.0-RC2, then 0.4.0 (2026-11-24). The page of a component on the 0.4.0 line keeps all three, newest first. The release candidate lines are no longer published: nothing they listed was dropped. This page is the entry point: it says what is new across the components, release by release, then where each one lists it.

[#rc2]
== Added in 0.4.0-RC2 (since 0.4.0-RC1)

Most of the work since RC1 follows one rule: Vidocq generates at build time what other runtimes do by reflection at start-up, and *the CLI and the Maven plugin carry the build-time constraints, not you*. A tutorial written and replayed from `vidocq create` to a Docker image found every place where that was not yet true; the list below is what changed.

=== Java modules: the tooling writes the directives

* **One check, written for you** — `vidocq doctor` and the build check the same module directives, the `opens` of the application's own packages included: the JPA entities, the types a REST resource takes or returns (through fields, getters, superclasses and implementations), the interceptors with a private method. `vidocq dev` writes a missing `opens` itself, `vidocq doctor --fix` and `vidocq:complete-module-info` write them on demand, and all of them keep one block marked `// vidocq:reflection`.
* **A clear message at run time** — a package the runtime cannot reach, and the build could not see, fails with the package and the `opens` line to add; under `vidocq dev` the line is written and the application reloads.
* **Or no directive at all** — `vidocq create --open-module` creates an `open module`.

Read: xref:0.4.0@vidocq::java-modules.adoc[Java modules in a Vidocq application].

=== Less reflection in an application

* **JSON-B bindings generated at build time** — Champollion generates the binding of the records and final classes a REST resource exchanges, with no annotation, so JSON-B maps them without reflection. xref:0.4.0@champollion::reference.adoc#rest-bindings[Champollion].
* **Interceptor methods called by generated code** — Vauban calls `@AroundInvoke`, `@AroundConstruct` and lifecycle interceptor methods through the provider generated in their package: a package-private interceptor needs no `opens`. xref:0.4.0@vauban::internals.adoc#components-provider[Vauban].
* **Repositories from a dependency jar** — a library's `@Repository` interfaces are implemented at build time, like the application's, by `vidocq:generate`. xref:0.4.0@mansart::usage.adoc#dependency-repositories[Mansart], xref:0.4.0@vidocq::whats-new.adoc#rc2[Vidocq].
* **Run-time generation is announced** — when Vauban, Cassini, Cyrano or Mansart must generate a class or serve a repository at run time instead of at build time, they say so in a framed warning at start-up.
* **What is generated, brick by brick** — each component's _Internals_ page now has a section, _Generated code and reflective fallback_, with the same table everywhere: what is generated, by which tool and when, what uses it at run time, what runs when it is missing, and how to tell which path ran. Start from xref:0.4.0@vidocq::internals.adoc#generated-code[Vidocq's], which lists every codegen bundle and links to each brick's.

=== The CLI does the setup

* **Dev services wired by `extension add`** — the dev-service provider, the JDBC driver and the test-scope pair are written into the `pom.xml`, the settings each extension needs into `vidocq.properties` (commented when only you can know the value), and `vidocq config set` uncomments a line in place. `vidocq doctor` and `vidocq:checkpom` warn about anything missing.
* **Docker from macOS and Windows** — `vidocq build docker` links the runtime image inside a Linux JDK stage of the Dockerfile and builds the image when Docker answers.
* **Quieter builds** — the "created in the last round" warnings are gone, Mansart's generated sources included.

Full list: xref:0.4.0@vidocq::whats-new.adoc#rc2[What's new in Vidocq Runtime].

=== SNAPSHOTs on our own repositories

`main` of every component publishes its SNAPSHOTs to `https://maven.vidocq.dev/snapshots/`, copied every 10 minutes to `https://maven.bak.vidocq.dev/snapshots/`, then to Central's snapshot repository. `vidocq create` declares the first two. Releases stay on Maven Central.

== How these lists are maintained

This page is versionless, so a link from here to a component resolves against that component's latest **final** release unless it says otherwise. The links are therefore pinned: `0.4.0@` for the 0.4.0 line, `dev@` for the development line.

When a release replaces a release candidate of its train, the release cut keeps the entries of the retired line: the What's new page of each component on the new line becomes cumulative (`scripts/cumulate-whats-new.js`), and the [.tag-new]#NEW# badges are stripped from the pages they were flagging on `main`. The cut does not touch this page: it is updated by hand when a component starts or stops having something to announce.
