All the modules but Erasmus and Tassis live in one repository, `Vidocq/vidocq`, and are released together under one version. Vidocq Runtime assembles them through a Quarkus-inspired extension SPI. A dotted arrow is an integration that is optional, or that the Vidocq Runtime extension assembles.

== Why a new runtime?

Three reasons:

. **Technical sovereignty.** The Jakarta world rests largely on a handful of historical foundations (Tomcat, Jetty, Netty, Hibernate, Yasson, ArC, RESTEasy). Remarkable work, but accumulated dependencies. Vidocq bets on rebuilding everything on pure Java 25, leaning on what the JDK now offers: virtual threads, scoped values, Class-File API, strict Java Modules.

. **Compile-time generation.** No runtime reflection, no dynamic proxies, no ASM, no Byte Buddy. Anything computable at `compile-time` is computed at `compile-time`. At startup, we instantiate. The JDK's AOT cache (Project Leyden) works on a packaged application; a GraalVM `native-image` is not available yet.

. **Sober historical inspiration.** Each component honours a French figure from the late 18th / early 19th century whose method captures the spirit of the module. An aesthetic stance, not a pastiche.

== Status

[CAUTION]
====
The suite is released on **Maven Central** as an **alpha**: APIs may still change and production use is not recommended yet. Bug reports from early adopters are very welcome on https://codefloe.com/Vidocq[Codefloe].
====

The documentation you are reading is versioned: the default pages describe the
**latest release**, and the `dev` version of each component (version selector in
the sidebar) follows `main`, the development line.

What works today:

* Chappe — HTTP/1.1, HTTP/2, WebSocket (RFC 6455), virtual threads, RFC 9110/9112/9113 conformance.
* Vauban — build-time CDI 4.1 Lite, official CDI Lite TCK **774/774**.
* Cassini — Jakarta REST 4.0, official TCK green on every test that applies to the Core Profile (xref:cassini::tck.adoc[TCK status]).
* Champollion — JSON-P 2.1 (**179/179**) + JSON-B 3.0 (**290/295**, the 5 others are disabled in the TCK itself), APT generation.
* Foy — Servlet 6.1, official TCK **1707 passing of 1714 run** (the 7 skipped are HTTP/2 server push); Jakarta WebSocket 2.2 server, programmatic API.
* Peano — Jakarta Expression Language 6.0, official TCK **361/361** (new in 0.4.0).
* Ibarra — Jakarta Pages 4.0, pages precompiled at build time, on Foy and Peano, official TCK **682/682** (new in 0.4.0).
* Bodoni — Jakarta Standard Tag Library 3.0; the official Tags tests pass **541/541** on Ibarra, Foy and Peano, a compatibility measurement, not a certification (new in 0.4.0).
* Vidocq Runtime — orchestrator and CLI; the assembled runtime passes **1888 official MicroProfile TCK tests** across all eight component specs (Config, Health, Metrics, Fault Tolerance, JWT, Rest Client, Telemetry, OpenAPI) — the seven of the MicroProfile 7.2 platform, OpenAPI and Telemetry on its release-candidate TCKs, plus Metrics; its Jakarta EE Core Profile 11 compatibility request is filed and accepted.
* MicroProfile bricks — Config (Ravel), Health (Knock), Metrics (Dirac), Fault Tolerance (Heisenberg), JWT (Cervantes), Rest Client (Cyrano), Telemetry (Humboldt), OpenAPI (Grimm), each wired into Vidocq Runtime through an extension and covered by its own TCK page.

In preview (released, not complete or not certified):

* Noether — Jakarta Persistence 3.2, extracted from Mansart (Mansart keeps Jakarta Data 1.0, which already ships); new in 0.4.0.
* Kerckhoffs — Jakarta Security 4.0: identity stores, BASIC and FORM authentication, `@RememberMe`, authorization of web resources; new in 0.4.0.

Work in progress:

* Tassis — Jakarta Messaging 3.1 with an in-memory broker, in the JVM or over AMQP 1.0 (official TCK 903/903 of the applicable tests, not released yet).
* Erasmus — Jakarta Validation 3.1 (engine and built-in constraints working, not released yet).
* Jakarta WebSocket 2.2 — annotated endpoints and the official TCK, on Foy.
* HTTP/3 / QUIC — Chappe, planned.

Full per-module breakdown: xref:roadmap.adoc[Consolidated roadmap].
