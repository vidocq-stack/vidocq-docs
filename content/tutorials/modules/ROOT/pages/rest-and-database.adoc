= REST + database
:description: Add persistence to a Vidocq application — a Jakarta Data repository (Mansart) over a pooled datasource, transactions, Flyway migrations, and PostgreSQL started for you in dev mode and tests.

[.lead]
This tutorial continues from xref:your-first-app.adoc[Your first Vidocq application] and gives the app a real database: a `Product` entity, a Jakarta Data repository generated at compile time by Mansart, a virtual-thread-native connection pool, `@Transactional` methods and a Flyway migration. In dev mode and in tests, a PostgreSQL container is started for you. Like the first tutorial, it follows the `{project-version}` development line.

== What you will build

* `GET /products`, `GET /products?name=…` and `POST /products`, backed by PostgreSQL;
* a `ProductRepository` interface — its implementation is *generated at compile time*, no run-time proxy;
* transactions handled by Mansart's Jakarta Transactions manager through Vauban interceptors;
* the schema created by a Flyway migration.

== Prerequisites

* The `todo` project from xref:your-first-app.adoc[the first tutorial] (or any project created with `vidocq create -x cassini-rest`).
* **Docker**: dev mode and the tests start PostgreSQL in a container (Testcontainers).

== Step 2 — The schema

Create `src/main/resources/db/migration/V1__products.sql`:

[source,sql]
----
CREATE TABLE products (
    id    BIGSERIAL PRIMARY KEY,
    name  VARCHAR(255) NOT NULL,
    price DOUBLE PRECISION NOT NULL
);
----

Flyway applies it to the `@Default` datasource when the application starts, and records it so it runs once.

== Step 3 — The entity

Create `src/main/java/com/acme/todo/products/Product.java`:

[source,java]
----
package com.acme.todo.products;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue
    private Long id;

    private String name;

    private double price;

    public Product() {
    }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public double getPrice() { return price; }
    public void setPrice(double price) { this.price = price; }
}
----

Mansart implements Jakarta Data 1.0 and reads the standard Jakarta Persistence annotations for its entity model — at *compile time*, through its annotation processor.

== Step 4 — The repository

Create `src/main/java/com/acme/todo/products/ProductRepository.java`:

[source,java]
----
package com.acme.todo.products;

import jakarta.data.repository.BasicRepository;
import jakarta.data.repository.Repository;
import jakarta.transaction.Transactional;

import java.util.List;

@Transactional
@Repository
public interface ProductRepository extends BasicRepository<Product, Long> {

    List<Product> findByNameLike(String pattern);
}
----

You write the interface; the Mansart annotation processor generates `ProductRepositoryImpl` during compilation and Vauban registers it as a bean. `findByNameLike` is a *derived query*: the SQL comes from the method name. `@Transactional` on the interface makes every method run in a transaction, through the interceptor chain Vauban generates.

== Step 5 — The resource

Create `src/main/java/com/acme/todo/products/ProductResource.java`:

[source,java]
----
package com.acme.todo.products;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;
import jakarta.ws.rs.Consumes;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.POST;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.QueryParam;
import jakarta.ws.rs.core.MediaType;

import java.util.List;

@Path("/products")
@ApplicationScoped
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class ProductResource {

    @Inject
    ProductRepository products;

    @GET
    public List<Product> list(@QueryParam("name") String name) {
        return name == null ? products.findAll().toList() : products.findByNameLike("%" + name + "%");
    }

    @POST
    public Product add(Product product) {
        return products.save(product);
    }
}
----

== Step 6 — Run it in dev mode

[source,bash]
----
vidocq dev
----

The first start pulls the PostgreSQL image; the dev service then starts a container, hands its URL and credentials to the pool, and Flyway creates the table. As in the first tutorial, the build opens the new package for you:

[source]
----
[INFO] ✔ module-info.java: opens com.acme.todo.products;   (com.acme.todo.products.Product, …)
----

Try it:

[source,bash]
----
curl -X POST http://localhost:8080/products \
     -H 'Content-Type: application/json' \
     -d '{"name":"Optical telegraph","price":1794.0}'
curl -X POST http://localhost:8080/products \
     -H 'Content-Type: application/json' \
     -d '{"name":"Semaphore","price":12.5}'

curl http://localhost:8080/products
curl 'http://localhost:8080/products?name=tele'
----

[source,json]
----
[{"id":1,"name":"Optical telegraph","price":1794.0},{"id":2,"name":"Semaphore","price":12.5}]
[{"id":1,"name":"Optical telegraph","price":1794.0}]
----

Insert, query, transaction commit — all through code generated at build time.

== Step 8 — Outside dev mode

The packaged application (`vidocq build`, `vidocq build docker`) does not start containers: give it its database. Set the three pool keys, for instance:

[source,bash]
----
vidocq config set vidocq.pool.url jdbc:postgresql://db.example.com:5432/todo
vidocq config set vidocq.pool.username todo
----

`vidocq config set` uncomments the line of the block in place. A password belongs in the environment rather than in the file: like every configuration key, `vidocq.pool.password` can be given as the environment variable `VIDOCQ_POOL_PASSWORD`.

== Going further

* **Named datasources** — declare a second pool with `vidocq.pool.<name>.*` keys and route a repository to it with `@Repository(dataStore = "<name>")`; `@Inject @Named("<name>") DataSource` injects it anywhere. See xref:dev@vidocq::modules/vidocq-runtime-extensions.adoc[the runtime extensions page] for the setup.
* **Repositories shipped in a library** — `@Repository` interfaces of a dependency jar are implemented at build time like yours. See xref:dev@mansart::usage.adoc#dependency-repositories[Mansart usage].
* xref:dev@mansart::usage.adoc[Mansart usage] — derived queries, JDQL, pagination, pool sizing.
* xref:dev@mansart::concepts.adoc[Mansart concepts] — how the repository implementations are generated.
* xref:dev@vidocq::dev-services.adoc[Dev services] — the PostgreSQL, Keycloak and OpenTelemetry dev services, their settings and how to turn them off.
* The complete runnable example: `vidocq-runtime-examples/vidocq-runtime-mansart-h2-example` in {repo-vidocq}[Vidocq/vidocq] — H2, XA transactions, OpenAPI and a small UI on top of what you just built.
