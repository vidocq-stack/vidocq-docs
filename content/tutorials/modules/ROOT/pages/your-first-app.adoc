= Your first Vidocq application
:description: From nothing to a running REST service — install the CLI, scaffold a project, serve JSON, work in dev mode, test, and package it as a Docker image.

[.lead]
In this tutorial you install the Vidocq CLI, scaffold a REST application called `todo`, serve JSON from it, watch it reload in dev mode, run its tests, and package it as a Docker image. Around twenty minutes, no prior Vidocq knowledge assumed. It follows the `{project-version}` development line: the CLI and the artifacts come from `https://maven.vidocq.dev/snapshots/`, where every build of `main` is published.

== What you will build

A small `todo` HTTP API:

* `GET /hello` — a plain-text sanity check;
* `GET /todos` and `POST /todos` — a JSON list, serialized automatically;
* `GET /health` — a health check, added as an extension.

Under the hood you will be running the real thing: the Chappe HTTP server on virtual threads, Cassini (Jakarta REST 4.0), Vauban (CDI 4.1 Lite) and Champollion (JSON-B), all wired at *compile time*. No classpath scanning and no proxies at boot: that is why the application starts in well under a second.

You never edit the `pom.xml` or `module-info.java` by hand in this tutorial: the CLI writes what each step needs.

== Prerequisites

* **Java 25** (Temurin recommended) — check with `java -version`
* **Docker** (Docker Desktop, OrbStack, Podman…) for the last step only

You do not need Maven installed: every project comes with the Maven wrapper (`./mvnw`).

TIP: With https://sdkman.io[SDKMAN!]: `sdk install java 25-tem`.

== Step 1 — Install the CLI

[source,bash]
----
curl -fsSL https://vidocq.dev/install.sh | VIDOCQ_VERSION=snapshot sh
----

On Windows (PowerShell):

[source,powershell]
----
$env:VIDOCQ_VERSION = "snapshot"; irm https://vidocq.dev/install.ps1 | iex
----

The script downloads the latest CLI of the development line into `~/.vidocq/cli` and puts a `vidocq` launcher in `~/.local/bin`. Verify:

[source,bash,subs=attributes+]
----
$ vidocq version
Vidocq CLI {project-version} (built …)
----

NOTE: Without `VIDOCQ_VERSION=snapshot`, the script installs the latest release from Maven Central; this tutorial then needs the {release-version} version of these pages.

== Step 2 — Scaffold the project

[source,bash]
----
vidocq create --name todo --group-id com.acme --extension cassini-rest
cd todo
----

`--extension cassini-rest` (short: `-x`) enables Jakarta REST — it brings the Chappe HTTP server, CDI (Vauban) and JSON-B (Champollion). What you get is a standard Maven project with Java modules:

[source]
----
todo/
  pom.xml                                     <1>
  mvnw, mvnw.cmd, .mvn/wrapper/               <2>
  src/main/java/
    module-info.java                          <3>
    com/acme/todo/HelloResource.java          <4>
  src/main/resources/
    vidocq.properties                         <5>
  src/test/java/com/acme/todo/
    HelloResourceTest.java                    <6>
  README.md, .gitignore
----
<1> The build descriptor, without a parent: it imports the Vidocq BOM, declares `vidocq-runtime-maven-plugin` as a build extension, and lists the dependencies. See <<the-pom,the pom below>>.
<2> The Maven wrapper: no local Maven needed.
<3> The module descriptor, with the `requires` and `opens` the REST extension needs, each marked `// vidocq:cassini-rest`.
<4> A first resource, `GET /hello`.
<5> Configuration (`vidocq.http.port=8080`, …).
<6> A test that starts the application and calls `/hello`.

Worth knowing in it:

* *No parent.* The pom imports `vidocq-runtime-bom` (the versions of every Vidocq artifact) and declares `vidocq-runtime-maven-plugin` with `<extensions>true</extensions>`. As a build extension, the plugin completes the build before any goal runs: it binds its goals (`generate`, `check-module-info`, `package`, …), pins the versions of the lifecycle plugins, and supplies the compiler release and the source encoding where a pom does not name them. That is what `vidocq-runtime-parent` used to carry, so a plain `./mvnw package` still produces a runnable distribution. An `[INFO] [vidocq] todo: no Vidocq parent in the pom, the plugin adds …` line at the top of the build log names what it added.
* *One version.* `vidocq.version` drives both the BOM and the plugin; change it in one place to move to another Vidocq version. The pom also names `maven.compiler.release` and `project.build.sourceEncoding` itself, so an IDE that reads the pom without running the plugin sees them.
ifeval::["{docs-line}" == "dev"]
* *Snapshot repositories.* This tutorial follows the development line, so the pom declares `maven.vidocq.dev` (and its mirror `maven.bak.vidocq.dev`) as repository and plugin repository for the SNAPSHOTs. A project created from a release does not write them: Maven Central is enough.
endif::[]
* *Dependencies.* `vidocq-runtime-core` and the extension you chose (`vidocq-runtime-cassini-rest-extension`), plus the test dependencies. There is no version on them: the BOM manages it.

NOTE: `vidocq create --with-parent` writes the previous style, a pom that inherits `io.vidocq.runtime:vidocq-runtime-parent`. `vidocq pom convert --to parentless` (or `--to parent`) moves an existing pom from one style to the other. Both builds give the same result; see xref:dev@vidocq::modules/vidocq-runtime-maven-plugin.adoc#parentless[An application without the parent].

There is no main class: the runtime boots the application (`vidocq create --main` adds one, for an IDE Run configuration). Run `vidocq extension list --available` to see every extension, and `vidocq create --help` for the options (`--package`, `--open-module`, …).

== Step 3 — Build and run

[source,bash]
----
vidocq build
sh target/todo-1.0.0-SNAPSHOT/bin/todo.sh
----

`vidocq build` runs `./mvnw package`: it compiles, runs the code generators, and assembles a distribution under `target/todo-1.0.0-SNAPSHOT/` (launchers in `bin/`, the application and its own libraries in `app/`, the runtime and its bricks in `lib/`, also zipped as `target/todo-1.0.0-SNAPSHOT-dist.zip`). In another terminal:

[source,bash]
----
$ curl http://localhost:8080/hello
Hello from Vidocq!
----

The log line to look for:

[source]
----
[INFO ][…][main][i.v.r.c.VidocqBootstrap#start] : Vidocq - Started in 118.963 ms (process running for 209 ms)
----

.What just happened?
[NOTE]
====
During the build, code generators ran: the Cassini processor turned `@Path` and `@GET` into a static dispatch adapter, the Vauban processor resolved the CDI graph and generated the beans' factories, and the Vidocq plugin checked the module directives and assembled a module-path distribution. At boot the runtime *instantiates* what was computed at build time. That is the whole Vidocq philosophy in one build.
====

Stop the application (Ctrl+C) before the next step.

== Step 4 — Dev mode

Rebuilding after each change gets old quickly. Dev mode runs the application and rebuilds it on each change:

[source,bash]
----
vidocq dev
----

Leave it running. Edit the text in `HelloResource`, save, and `curl` again: the new text is served a few seconds later, without a restart of the JVM. Dev mode also starts the xref:dev@vidocq::dev-services.adoc[dev services] your extensions need (none yet) and serves the dev console.

== Step 5 — Serve JSON

Still in dev mode, add a `todos` package. Create `src/main/java/com/acme/todo/todos/Todo.java`:

[source,java]
----
package com.acme.todo.todos;

public record Todo(String title, boolean done) {
}
----

And `src/main/java/com/acme/todo/todos/TodoResource.java`:

[source,java]
----
package com.acme.todo.todos;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.ws.rs.Consumes;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.POST;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;

@Path("/todos")
@ApplicationScoped
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class TodoResource {

    private final List<Todo> todos = new CopyOnWriteArrayList<>();

    @GET
    public List<Todo> list() {
        return todos;
    }

    @POST
    public Todo add(Todo todo) {
        todos.add(todo);
        return todo;
    }
}
----

Save, and try it:

[source,bash]
----
curl -X POST http://localhost:8080/todos \
     -H 'Content-Type: application/json' \
     -d '{"title":"write my first Vidocq app","done":true}'

curl http://localhost:8080/todos
----

[source,json]
----
[{"title":"write my first Vidocq app","done":true}]
----

JSON serialization is handled by Champollion (JSON-B 3.0): no annotation, no configuration.

.No reflection, no `opens`
[NOTE]
====
An application is a Java module, and JSON-B would normally read `Todo` by reflection, which needs its package opened. Here it does not: `Todo` is a record a resource returns, so the build generates its JSON-B binding — plain code that reads and writes it, without reflection — and there is nothing to open.

When a type does keep the reflective mapping (one the generated code cannot map — an abstract class or an interface as a property type, a getter overridden in a subclass, … — named in the build output), its package must be opened: `vidocq dev` writes the line into `module-info.java` itself, in a block marked `// vidocq:reflection`; outside dev mode, `./mvnw package` stops with that line, and `vidocq doctor --fix` writes it. xref:dev@vidocq::java-modules.adoc[Java modules in a Vidocq application] explains what is generated, what is checked, and how to opt out with an `open module`.
====

== Step 6 — Test

The scaffolded `HelloResourceTest` starts the application and calls it. Run the tests continuously while you work:

[source,bash]
----
vidocq test
----

It runs every test, then again on each change of the main or test sources. The summary line ends with the keys: type `r` and Enter to run every test again, `f` for the failed ones, `q` to quit. In a CI, run them once with `./mvnw test`.

TIP: If you changed the text of `HelloResource` in Step 4, the test now fails: it expects `Hello from Vidocq!`. Put the text back, or update the test.

== Step 7 — Add extensions as you grow

Every capability is an extension — health checks, metrics, persistence, JWT security, OpenAPI…:

[source,bash]
----
vidocq extension list --available
vidocq extension add knock-health
----

`extension add` writes the dependency into `pom.xml` and the `requires` into `module-info.java`; for extensions with a dev service or settings, it also writes those (xref:rest-and-database.adoc[the next tutorial] shows it). Restart `vidocq dev`, then:

[source,bash]
----
$ curl http://localhost:8080/health
{"status":"UP","checks":[]}
----

`vidocq doctor` checks the whole project (extensions, module directives, dev services) and `vidocq doctor --fix` repairs what it can.

== Step 8 — Package for production

[source,bash]
----
vidocq build jlink    # self-contained runtime image (no local java needed)
vidocq build docker   # container image
----

`vidocq build docker` links a minimal runtime image and wraps it in a distroless image. On macOS and Windows, where the local `jlink` produces a macOS or Windows image, the generated Dockerfile links it again inside a Linux JDK stage; when Docker answers, the CLI builds the image:

[source]
----
[INFO] The runtime image was linked for macOS (Mach-O executable): the Dockerfile links it again inside eclipse-temurin:25-jdk (Linux).
[INFO] Docker image built: todo:1.0.0-SNAPSHOT
✔ Docker image built.
----

Run it:

[source,bash]
----
docker run --rm -p 8080:8080 todo:1.0.0-SNAPSHOT
curl http://localhost:8080/hello
----

Without Docker, the CLI says so and prints the `docker build` command to run later. See xref:dev@vidocq::usage.adoc[Usage] for jlink, jpackage and Docker options.
