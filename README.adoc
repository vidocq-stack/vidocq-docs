= vidocq-docs

The documentation site of the Vidocq ecosystem — https://doc.vidocq.dev.

An https://antora.org[Antora] site aggregating the `docs/en` component of every
sub-project (16 bricks), plus two site-level components hosted in this repo:
`content/home` (landing) and `content/tutorials` (cross-brick guides). The
shared UI bundle (`ui-bundle/`) carries the visual identity, the version
selector and the search box — never customise the UI per project.

The site is **English-only** and **versioned** — see
`docs/adr/0004-english-only-versioned-search.md`.

== Prerequisites

* Node.js 20+ (`npm`)
* network access to the sibling clones (local build) or codefloe.com (prod build)
* optional: access to https://kroki.vidocq.dev (mermaid diagrams; any kroki
  server works via `--attribute kroki-server-url=...`)

== Local build

[source,bash]
----
# 1. build the UI bundle (once, or after any ui-bundle/src change)
cd ui-bundle && npm ci && npx gulp bundle && cd ..

# 2. build the site from the local sibling clones
npm ci
npx antora antora-playbook-local.yml       # reads ../<repo> refs main + docs/0.2.0

# 3. serve it
npx http-server build/site -p 8080
----

The local playbook reads each sibling repo's `main` and `docs/0.2.0` refs
directly from `.git`; a repo whose working tree has `main` checked out is read
from the working tree (uncommitted docs edits show up — handy for preview).
Always `rm -rf build/site` before rebuilding if components were removed.

The prod playbook (`antora-playbook.yml`) is the same site built from
`https://codefloe.com/Vidocq/*` over anonymous HTTPS.

== Deployment

`.forgejo/workflows/deploy-pages.yaml` builds the UI bundle and the site on
every push to `main`, then deploys `build/site` to **Cloudflare Pages**
(project `vidocq-docs`) with `wrangler pages deploy` — secrets
`CF_API_TOKEN` / `CF_ACCOUNT_ID`. Every sub-project carries a
`notify-docs.yml` workflow that triggers this deploy whenever a push to its
`main` or `docs/*` branches touches `docs/**`.

NOTE: The `Dockerfile`, `chappe-config.yml` and `deploy/` compose files are
the legacy self-hosted serving path (Chappe + Portainer); they are kept for
reference but no workflow uses them.

== Versioned docs — release runbook

Released bricks build two doc lines: branch `docs/<version>` (site default,
no URL segment) and `main` (Antora version `dev`, `prerelease: true`, served
under `/<component>/dev/`). Artifact versions in pages come from the
`project-version` / `release-version` attributes set per branch in
`docs/en/antora.yml`.

On release train X:

. in each released repo: `git branch docs/X main`, then on that branch set
  `version: 'X'`, `project-version: X`, drop `prerelease: true`;
. on `main`: bump `project-version` to the next SNAPSHOT;
. here: add `docs/X` to the `branches:` list of both playbooks.

== Adding a new component

. In the sub-project: create `docs/en/antora.yml` + `modules/ROOT/{nav.adoc,pages/}`
  following the **Vauban** gold-reference layout (see `CLAUDE.md` for the
  canonical page order and rules).
. Add the repo to `content.sources` of both playbooks (`branches: [main]`
  until its first release).
. Add its name to `ORDER_BASE` in `ui-bundle/src/helpers/components-quick-nav.js`
  to position it in the sidebar (otherwise it lands alphabetically at the tail).
. Add a row to the components table of `content/home/modules/ROOT/pages/index.adoc`
  and a repo attribute (`repo-<name>`) to both playbooks.
. Give the sub-project a `.forgejo/workflows/notify-docs.yml` (copy from any brick).

== Contributing to a module's docs

Edit `docs/en` in the module's own repo — this repo only aggregates. Keep the
canonical section order; never hardcode artifact versions (use the
attributes); test any new mermaid block against kroki (a syntax error makes
kroki *silently* skip the diagram). Conventions live in `CLAUDE.md` / `AGENTS.md`.
