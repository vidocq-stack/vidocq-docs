= vidocq-docs
:toc: macro
:source-highlighter: highlight.js

Documentation Antora de l'écosystème **Vidocq** — multi-component, bilingue (FR canonique + EN), servie par xref:../chappe[Chappe].

Ce dépôt **n'héberge pas le contenu** des modules. Chaque module (`vidocq`, `vauban`, `cassini`, `champollion`, `chappe`, `foy`, `mansart`) garde sa propre documentation dans son répertoire `docs/`. `vidocq-docs` ne contient que :

* la *playbook* Antora (`antora-playbook.yml`) ;
* le UI bundle XIXᵉ siècle (`ui-bundle/`) ;
* la home (`content/home-{en,fr}/`) ;
* le `Dockerfile` qui tire `chappe-cli` depuis repolite (cf. link:docs/adr/0003-chappe-cli-from-repolite.md[ADR 0003]) ;
* le workflow Forgejo Actions et les compose de déploiement Portainer (`deploy/`).

toc::[]

== Pré-requis

* **Node LTS** (≥ 20) — pour Antora et le UI bundle.
* **Java 25** + **Maven** — uniquement pour le build Docker (le `chappe-fetcher` qui tire `chappe-cli` depuis repolite).
* Accès à `https://repo.vidocq.dev/snapshots` (lecture) — d'où vient `chappe-cli`.
* Accès aux **clones frères** des sept modules pour le build local :
+
[source,text]
----
parent/
├── vidocq-docs/         (ce repo)
├── vidocq/
├── vauban/
├── cassini/
├── champollion/
├── chappe/
├── foy/
└── mansart/
----

== Build local

Le plus court — un script pilote tout :

[source,bash]
----
bash scripts/build-local.sh                # UI bundle + Antora + fetch version Chappe + fetch fonts
bash scripts/build-local.sh --skip-fonts   # idem, sans tenter de télécharger les WOFF2
bash scripts/build-local.sh --ui-only      # juste le UI bundle
bash scripts/build-local.sh --site-only    # juste Antora (UI déjà bâti)
bash scripts/build-local.sh --serve        # build + serve sur http://localhost:8080
----

Ou à la main, étape par étape :

[source,bash]
----
# 1. UI bundle (CSS + JS + helpers + fonts + zip)
cd ui-bundle
npm install
node ../scripts/fetch-chappe-version.js   # met à jour src/data/versions.json
bash ../scripts/fetch-fonts.sh             # télécharge les WOFF2 (optionnel)
npm run build
cd ..

# 2. Site Antora à partir des clones frères
npx antora@^3.1.0 antora-playbook-local.yml

# Sortie : ./build/site
----

== Build Docker (avec Chappe)

[source,bash]
----
docker build \
  --build-arg CHAPPE_VERSION=0.1.0-SNAPSHOT \
  --build-arg MAVEN_REPO_URL=https://repo.vidocq.dev/snapshots \
  -t vidocq-docs:test .
docker run --rm -p 8080:8080 vidocq-docs:test
# → http://localhost:8080
----

Le contexte de build est uniquement ce repo : plus besoin de cloner `chappe`
en frère, le `Dockerfile` tire `chappe-cli-shaded` depuis repolite (cf. link:docs/adr/0003-chappe-cli-from-repolite.md[ADR 0003]).

Variables d'environnement reconnues par l'`entrypoint.sh` du container :

[cols="1,3"]
|===
| Variable | Rôle

| `CHAPPE_DOCROOT` | Répertoire racine du site (défaut : `/var/www/vidocq-docs`)
| `CHAPPE_PORT`    | Port d'écoute (défaut : `8080`)
| `CHAPPE_BIND`    | Adresse de bind (défaut : `0.0.0.0`)
| `CHAPPE_GZIP`    | Active `--gzip` côté CLI (défaut : `true`)
| `STAGING`        | Loggué pour info ; le header `X-Robots-Tag` sera injecté quand la CLI Chappe exposera `--header-if-env`
|===

Build args du `Dockerfile` :

[cols="1,3"]
|===
| Build arg | Rôle

| `CHAPPE_VERSION` | Coordonnée Maven de `chappe-cli` (défaut : `0.1.0-SNAPSHOT`)
| `MAVEN_REPO_URL` | URL repolite (défaut : `https://repo.vidocq.dev/snapshots` ; pointer sur `/releases` pour un tag stable)
|===

== Déploiement (Portainer + Nginx Proxy Manager)

L'image est buildée par le workflow Forgejo Actions (`.forgejo/workflows/build.yml`)
et publiée sur la **container registry Forgejo** (intégrée à Forgejo ≥ 1.20) :

* `forge.vidocq.dev/vidocq/vidocq-docs:snapshot` — écrasé à chaque push sur `main`
* `forge.vidocq.dev/vidocq/vidocq-docs:latest`   — écrasé à chaque tag `v*`
* `forge.vidocq.dev/vidocq/vidocq-docs:0.1.0`    — tag immutable par version

Portainer consomme cette image via une **Stack-from-Git** qui pointe sur ce repo
et lit `deploy/compose.staging.yml` ou `deploy/compose.prod.yml`.

=== 1. Côté Forgejo — token registry

Sur Forgejo, *Settings → Applications → Generate Token* :

* Nom : `vidocq-docs-ci` (ou ce qu'on veut)
* Scopes : `write:package`, `read:package`

Le scope `read:repository` n'est plus nécessaire depuis l'ADR 0003 (le
Dockerfile ne clone plus `vidocq/chappe`, il tire `chappe-cli` depuis repolite).

Le token est utilisé par le workflow Forgejo Actions (secret `REGISTRY_TOKEN`)
et par Portainer pour pull l'image (cf. étape suivante). Côté secrets de repo :

[cols="1,2"]
|===
| Secret | Valeur

| `REGISTRY_USER`             | utilisateur ou bot avec `write:package`
| `REGISTRY_TOKEN`            | token généré ci-dessus
| `PORTAINER_WEBHOOK_STAGING` | URL de webhook Portainer (étape 3)
| `PORTAINER_WEBHOOK_PROD`    | URL de webhook Portainer (étape 3)
|===

NOTE: Forgejo Actions **réserve le préfixe `FORGEJO_`** pour les secrets internes ;
on utilise donc `REGISTRY_*` côté secrets utilisateur.

=== 2. Côté Portainer — déclarer la registry Forgejo

*Settings → Registries → Add registry → Custom* :

* URL : `forge.vidocq.dev`
* Authentification : *Yes*
* Username / Password : le couple `REGISTRY_USER` / `REGISTRY_TOKEN`

C'est ce qui permet à Portainer de tirer les images privées.

=== 3. Côté Portainer — créer la stack (staging et prod)

*Stacks → Add stack → Repository* :

[cols="1,2"]
|===
| Champ | Valeur

| Repository URL          | `https://forge.vidocq.dev/vidocq/vidocq-docs`
| Repository reference    | `refs/heads/main`
| Compose path            | `deploy/compose.staging.yml` (ou `deploy/compose.prod.yml`)
| Authentification        | token Forgejo si le repo est privé
| GitOps updates          | *Polling*, intervalle `5m` (recommandé) **ou** *Webhook*
| Environment variables   | `IMAGE_TAG=snapshot`, `CONTAINER_NAME=vidocq-docs-staging`
|===

Dans la même page, copier le **webhook URL** affiché par Portainer et le coller
dans les secrets Forgejo (`PORTAINER_WEBHOOK_STAGING` ou `_PROD`). Le workflow
poke ce webhook après chaque `docker push`, ce qui force Portainer à re-pull
l'image et à `docker compose up -d`.

=== 4. Côté Nginx Proxy Manager

NPM tourne sur l'hôte et partage le réseau Docker `reverseproxy_default` avec
le container `vidocq-docs`. Le compose attache le service à ce réseau **sans
exposer de port sur l'hôte**.

*Hosts → Proxy Hosts → Add Proxy Host* :

[cols="1,2"]
|===
| Champ | Valeur staging / prod

| Domain Names    | `staging-doc.vidocq.dev` / `doc.vidocq.dev`
| Scheme          | `http`
| Forward Hostname | `vidocq-docs-staging` / `vidocq-docs-prod` *(le `container_name` du compose)*
| Forward Port    | `8080`
| Block Common Exploits | activé
| Websockets Support    | inactif (pas de WS à ce stade)
| SSL → Force SSL       | activé (Let's Encrypt)
|===

NPM résout le `container_name` via le DNS Docker du réseau partagé.

=== 5. Vérifier

[source,bash]
----
# Healthcheck interne
docker exec vidocq-docs-staging wget -qO- http://localhost:8080/healthz
# → ok

# Healthcheck externe (depuis n'importe où)
curl -s https://staging-doc.vidocq.dev/healthz
# → ok

# Vérifier le X-Robots-Tag en staging
curl -sI https://staging-doc.vidocq.dev/ | grep -i x-robots-tag
# → X-Robots-Tag: noindex, nofollow
----

=== Rollback

Trois niveaux, du plus rapide au plus propre :

. **Tag immutable.** Sur la stack Portainer prod, surcharger
  `IMAGE_TAG=0.1.0` (ou la version stable précédente) → *Update the stack*.
. **Git revert.** `git revert <commit>` puis `git push`. Portainer redéploie
  via polling ou webhook.
. **Rebuild from tag.** Re-tagger un commit ancien (`git tag v0.0.x` puis push)
  → le workflow rebuilde et republie `:latest`.

=== Troubleshooting CI

==== `node: executable file not found in $PATH`

Le runner Forgejo par défaut tourne sur `docker:dind` (Alpine, pas de Node).
Le workflow surcharge déjà `container:` avec `catthehacker/ubuntu:act-22.04`
(Node 20 + Docker CLI). Si l'erreur revient, vérifier que la modif est en place.

==== `[/var/run/docker.sock] is not a valid volume, will be ignored`

Le bind-mount est filtré par la config `act_runner` parce que `valid_volumes`
est restrictif par défaut. Sur l'hôte qui héberge le runner, ajouter à la config :

[source,yaml]
----
# /etc/forgejo-runner/config.yaml (ou équivalent)
container:
  privileged: true                       # nécessaire pour docker build à l'intérieur
  valid_volumes:
    - /var/run/docker.sock
----

Puis redémarrer le service runner. Sans ce mount, `docker build/push` du workflow
échoueront en `Cannot connect to the Docker daemon`.

==== Échec du `mvn dependency:copy` (stage `chappe-fetcher`)

Le Dockerfile tire `chappe-cli-shaded` depuis `https://repo.vidocq.dev/snapshots`
au build. Si le stage échoue :

* vérifier que repolite est accessible depuis le runner (firewall, DNS) ;
* vérifier qu'une version `chappe-cli:0.1.0-SNAPSHOT:jar:shaded` existe sur
  repolite (côté chappe : `mvn -pl chappe-cli -am deploy`) ;
* si repolite est privé en lecture, ajouter un `~/.m2/settings.xml` au stage
  `chappe-fetcher` avec les creds (cf. ADR 0003).

==== `denied: requested access to the resource is denied` au push image

Le `REGISTRY_USER` / `REGISTRY_TOKEN` n'a pas `write:package` sur le namespace
`vidocq/`. Régénérer un token avec ce scope, ou demander à un admin Forgejo
d'ajouter l'utilisateur comme `Write` membre de l'organisation.

== Ajouter un nouveau component

. Dans le repo du module concerné, créer la structure :
+
[source,text]
----
<module>/docs/
├── en/
│   ├── antora.yml                 # name: <module>,    title: <Module>
│   └── modules/ROOT/
│       ├── nav.adoc
│       └── pages/{index,getting-started,concepts,reference,migration}.adoc
└── fr/
    ├── antora.yml                 # name: <module>-fr, title: <Module>
    └── modules/ROOT/
        ├── nav.adoc
        └── pages/{index,getting-started,concepts,reference,migration}.adoc
----

. Ajouter la source dans `vidocq-docs/antora-playbook.yml` (et `antora-playbook-local.yml` pour le build local).

. Ajouter une référence depuis la home (`content/home-fr/modules/ROOT/pages/index.adoc` et `content/home-en/...`).

== Contribuer à la doc d'un module existant

**Pas ici.** La doc d'un module vit dans ce module. Une PR sur `vauban/docs/` (par exemple) sera automatiquement reprise au prochain build du site.

== Convention bilingue

* **Le français est canonique.** Tu écris d'abord en FR, puis tu traduis en EN.
* Pas de mélange de langues dans une même page.
* Les exemples de code, noms d'API, FQN sont **identiques** dans les deux langues — seul le texte autour change.
* Les titres de pages sont traduits, mais les ancres Asciidoc (`[#getting-started]`) restent stables (anglais).
* Le toggle FR/EN du UI bundle calcule l'URL homologue côté client : si on est sur `/vauban/page.html`, le toggle pointe vers `/vauban-fr/page.html`.
